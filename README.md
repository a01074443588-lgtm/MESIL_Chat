# **MESIL Chat — AI 돌봄 브리핑**

> **대화는 입력이고, 돌봄 브리핑이 결과입니다.**

> **독립 공개 소스 후보:** 합성자료 기반 전체 회귀시험과 별도 설치 검증을 통과했으며 최종 개인정보·공개 범위 재검수를 기다립니다. 이 상태는 GitHub 공개 승인이나 새 운영 배포를 뜻하지 않습니다.

MESIL Chat(메실챗)은 요양현장의 채팅·음성·사진·손글씨 보고를 어르신별 **변화**, **이미 한 일**, **아직 확인할 일**, **기록 활용 후보**로 정리하고, 담당자가 모든 판단을 원문 근거로 다시 확인할 수 있게 하는 AI 업무지원 솔루션입니다.

- **결선 시연:** [https://chat.silvermedical.kr](https://chat.silvermedical.kr) — 합성자료 전용 발표환경
- **소스코드:** [MESIL Chat GitHub](https://github.com/a01074443588-lgtm/MESIL_Chat) — 예선 공개본, 결선 후보와 버전이 다릅니다.
- **심사 체험 범위:** 자체 제작한 합성자료와 발표 담당자가 제공하는 합성 직원 계정

> **배포 검증 기준: 2026년 9월 13일.** 공개 Chat 18130의 승인된 배포와 공개 기능시험이 완료됐습니다. 이 공개 소스 후보에는 원본 Git 이력과 운영자료가 없습니다. 개인 이름 대신 역할을 기재한 공개 대안입니다.

> 실제 민감정보를 사용하는 현장 실증 환경과 결선 시연 환경은 분리합니다.
> 심사위원에게는 더미데이터만 있는 `chat.silvermedical.kr`을 제공합니다.
> AI 결과는 공식 기록이나 의료적 판단이 아니며, 담당자가 원문과 실제 상황을
> 확인한 뒤 사용합니다.

## 2. AI 솔루션

### 2.1 문제 정의

시설장으로 현장을 운영하며 가장 답답했던 점은, 직원들이 이미 성실하게 보고한 내용을 다시 찾고 확인하고 옮겨 적는 데 또 시간을 써야 한다는 것이었습니다.
현장 청취와 실제 업무 확인에서 드러난 부담은 다음과 같았습니다.

- 카카오톡은 누구나 쉽게 사용할 수 있어 업무보고에 편리하지만, 여러 대화방과 개인 기기에 흩어진 과거 보고를 기관이 같은 기준으로 보존·검색·관리하기는 어렵습니다.
- 어르신의 작은 변화를 잘 보고했어도 그 내용이 인수인계, 상담, 급여제공기록 같은 다음 업무로 이어지지 못합니다.
- 보고를 올린 뒤 “확인했다”, “이후 어떻게 됐다”는 동료의 피드백이 부족해 조치가 끝났는지 알기 어렵습니다.
- 분명히 대화방에 보고한 내용과 나중에 작성된 서류가 서로 다르거나 빠지는 일이 반복됩니다.

이 문제는 직원이 보고를 하지 않아서가 아닙니다. **이미 열심히 남긴 보고가 업무의 다음 단계로 이어지는 구조가 없기 때문**입니다. MESIL Chat은 직원에게 새로운 복잡한 기록을 한 번 더 요구하지 않고, 익숙한 대화와 파일 공유를 그대로 사용하면서 그 안의 보고를 찾고, 확인하고, 다시 업무에 활용할 수 있게 만들었습니다.

#### “유료 클라우드 메신저를 쓰면 되지 않나요?”

유료 업무용 메신저는 대화 보관과 검색 문제를 상당 부분 해결할 수 있습니다.
그 장점을 부정하지 않습니다. 다만 일반 메신저만으로는 보고를 어르신별 변화, 이미 한 조치, 아직 확인할 일로 나누고, 동료의 피드백과 근거 원문을 연결해 다음 기록 업무로 이어 주기 어렵습니다.

MESIL Chat이 해결하려는 핵심은 메신저 저장 용량이 아니라 **장기요양 현장의 보고가 확인·후속조치·기록 활용으로 이어지게 만드는 것**입니다. 기관이 데이터와 퇴사자 접근권한을 직접 관리한다는 점도 일반 메신저와 구분되는 운영 목적입니다.

### 2.2 AI 솔루션 소개

#### 솔루션 개요

**한눈에 보는 해결 흐름**

```text
직원의 채팅·사진·음성·손글씨 보고
  → 로컬 이미지 판독 / 로컬 음성 받아쓰기
  → 어르신·사건·조치·미완료 확인 후보 연결
  → 어르신별 AI 돌봄 브리핑
  → 근거 원문과 AI 제안 대조
  → 직원 수정·확인·승인
  → 기록 활용 후보
```

AI가 대신 결론을 내리지는 않습니다. AI가 먼저 읽고 정리한 내용을 직원이 원문과 어르신의 실제 상태에 맞춰 확인하고, 틀린 부분을 고친 뒤 필요한 업무에 사용합니다. 특히 투약·처치·평가와 공식 서류의 최종 책임은 언제나 담당자에게 있습니다.

이 흐름을 통해 직원은 **달라진 점**, **이미 한 일**, **아직 확인할 일**, **기록에 활용할 수 있는 후보**를 한 화면에서 확인하고, 필요할 때 근거가 된 원문 대화와 첨부로 돌아갈 수 있습니다.

심사 체험은 결선 시연 주소의 일반 로그인 화면에서 시작합니다. 요양보호사 계정은
현장보고·첨부·읽음·답글을, 사회복지사 계정은 돌봄브리핑·근거 확인·기록 검토를
중심으로 사용합니다. 각 계정에 허용된 방과 기능만 열립니다. 기존 `/reviewer`
역할 선택과 45분 체험 세션은 이번 결선의 제공 방식에 포함하지 않습니다.
자세한 순서는 합성 체험 계정과 동선은 발표 담당자가 안내합니다를 참고하세요.

#### AI 활용 내용

| 구분 | 내용 |
|---|---|
| 사용한 AI 도구·모델 | 공개 배포 후 합성 호출의 텍스트는 로컬 태그 `qwen3.8-27b:q5_k_m`, 이미지는 `qwen3-vl:8b-instruct`, 음성은 faster-whisper의 `large-v3-turbo` 구성으로 검증. 텍스트 태그는 사용자 지정 이름이며 공식 모델명·배포 라이선스 증명이 아님 |
| AI가 담당하는 기능 | 사진·손글씨·문서 판독, 음성 받아쓰기, 흩어진 보고 정리, 변화·조치·미완료 확인 후보 제시, 업무 관련 확인사항 정리 |
| AI를 활용한 이유 | 직원들은 어르신을 돌보는 일만으로도 바쁩니다. 이미 성실히 남긴 보고를 다시 찾고 같은 내용을 여러 번 옮겨 적느라 정작 어르신을 살필 시간이 줄어드는 것이 안타까웠습니다. AI가 먼저 읽고 정리해 직원이 사람을 돌보고 서로 확인하는 일에 더 집중하도록 돕고 싶었습니다. |
| AI가 없었다면 어려웠던 부분 | 직원이 매일 수많은 대화를 다시 읽고, 사진과 문서의 글자를 직접 옮기며, 어르신별 변화와 후속조치를 하나씩 대조해야 합니다. AI는 이 반복 확인을 줄이고 중요한 보고가 교대 과정에서 묻히지 않도록 돕습니다. |

텍스트 모델은 돌봄 질문의 답변과 근거 연결을, 이미지·언어 모델(VL)은 사진·문서의
글자 판독(OCR)을, 음성 인식(STT)은 받아쓰기를 담당합니다. 합성 호출과 모델 변경 후
복구를 시험했습니다. 공개 배포 후 합성 요청에서도 위 구성을 확인했지만, 모든 후속 요청의 실제 모델은 각 호출 결과로 확인해야 합니다.
텍스트 사용자 지정 태그의 원본 모델·변환 출처와 이용조건은 아직 확정하지 못했습니다.

실제자료와 합성 시연자료의 구분, 처리 위치, 외부 전송 제한과 사람의 최종
검수 원칙은 아래 `4.4 개인정보 및 보안 확인`과 `4.5 개인정보·AI 윤리 항목`에서
설명합니다.

#### (선택) AI 성능 개선 시도

1. **빠른 기본 결과와 AI 보강 분리**

   규칙 기반 기본 요약과 AI 생성을 구분합니다. 모델 준비·생성 실패·근거 부족은
   상태로 안내하며, 원문 확인·수동 검토·재시도로 이어집니다. 기본 요약이
   표시되더라도 AI 답변 생성 성공으로 표시하지 않습니다.

2. **근거가 없는 결과 차단**

   모델이 입력에 없는 이름·수치·진단·완료 여부를 만들지 않도록 지시하고,
   결과의 근거 번호가 실제 선택 원문을 가리키는지 검사합니다. 근거번호가
   연결됐다는 사실만으로 답변 내용의 정확성이 보장되지는 않습니다.

3. **사람의 수정과 승인 전제**

   OCR 판독문과 어르신 연결을 직원이 먼저 검수하지 않으면 AI 초안을 만들 수
   없게 했습니다. 이름·시간·숫자·약·신체 부위·위험 표현은 자동 확정하지
   않습니다.

검증한 환경과 제한사항은 아래 `5. 현재 검증 범위와 한계`에 정리했습니다.

### 2.3 이용자용 가이드

#### 처음 사용할 때

1. PC나 모바일 브라우저에서 `https://chat.silvermedical.kr`을 엽니다.
2. 발표 담당자가 안내한 합성 직원 계정으로 로그인합니다.
3. 본인에게 허용된 방에서 합성 대화와 첨부를 확인합니다. 실제 돌봄자료는 입력하지 않습니다.
4. `AI 돌봄 브리핑`에서 기간과 어르신을 선택하고, 답변의 근거 원문을 엽니다.
5. 통화 체험을 안내받은 경우 두 기기를 같은 네트워크에 연결하고 화면을 켠
   상태에서 마이크·카메라 접근을 허용합니다. 상대가 수락한 뒤 연결·종료와
   채팅방 복귀를 확인합니다.

Chat은 GitHub와 `/downloads`에서 APK를 제공하지 않습니다. 이 공개 후보의
`mobile/`도 완성된 Android 빌드 프로젝트가 아니므로 APK를 직접 만들 수 없습니다.
Android에서는 모바일 브라우저나 PWA(홈 화면에 설치하는 웹앱)로 접속합니다.
Talk용 APK는 이 후보와 무관하며 포함하지 않습니다. 앞선 개발 앱 실기기 시험은
공개 Chat APK의 배포·잠금화면 수신 보장을 뜻하지 않습니다. 자세한 경계는
[APK 미제공·통화 환경 안내](docs/PUBLIC_INSTALL.md)에 정리했습니다.

#### 현장 보고하기

1. 해당 업무방에서 문자, 사진, 음성 또는 문서를 전송합니다.
2. AI가 판독한 사진·손글씨·문서와 음성 받아쓰기 결과를 원본과 대조합니다.
3. 틀린 판독문과 잘못 연결된 어르신을 수정합니다.
4. `AI 돌봄 브리핑`에서 먼저 확인할 어르신과 이유를 봅니다.
5. `근거 대화 보기`를 열어 변화·조치·미완료 확인의 원문을 확인합니다.
6. 필요한 문장만 기록 활용 후보로 사용하고 최종 기록은 담당자가 확정합니다.

#### 이용 시 주의사항

- AI 결과만 보고 투약·처치·진단·위험평가를 결정하지 않습니다.
- 수치, 약 이름, 신체 부위, 시간, 완료 여부는 반드시 원문과 대조합니다.
- 불필요한 주민등록번호, 연락처, 주소, 보호자 정보는 입력하지 않습니다.
- 실제 돌봄자료는 기관이 승인한 내부 처리 경로에서만 사용합니다. 외부 AI가
  표시되는 기능에는 실제 돌봄자료를 입력하지 않습니다.
- 오류나 부적절한 결과는 수정하거나 사용하지 않고 담당자에게 알립니다.

현장에서는 직원 대화방과 파일 공유를 실제 업무에 사용하고 있습니다. 사진 글자

2026년 9월 13일 공개 Chat 배포 후 합성자료로 5개 방, 메시지·첨부·검색,

- 채팅·사진·음성·손글씨를 별도 도구가 아니라 같은 업무흐름에서 다룰 수 있습니다.
- AI 결과와 근거 원문을 같은 화면에서 추적할 수 있습니다.

- 업무시간 절감률
- 기록 누락 감소율
- 사고 예방 효과
- 실제 직원 만족도
- AI 종합 정확도 100%

실제 직원의 참여 인원, 전후 소요시간, AI 초안 수정·폐기율, 발견한 미완료

- [ ] 공개 권한이 없는 기관 내부자료를 업로드하지 않았습니다.
- [ ] 테스트 결과 JSON과 화면 캡처에 실제 이름·주소·계정이 없는지 확인했습니다.
- [ ] 외부 자료·모델·오픈소스의 출처와 라이선스를 최종 확인했습니다.
- [ ] 비공개 DEV 저장소 주소와 보호 파일을 외부에 공유하지 않았습니다.
- [ ] 개인정보 처리방침과 AI 활용 안내를 이용자가 쉽게 확인할 수 있습니다.

### 4.5 개인정보·AI 윤리 항목

직원이 남긴 보고에는 어르신의 건강 상태와 사생활, 직원의 업무정보가 담길 수
있습니다. 내용을 잘 정리하는 것만큼, 누가 볼 수 있고 어디에 사용되는지를
분명히 하는 것이 중요하다고 보고 다음 다섯 항목을 점검하고 있습니다.

#### 4.5.1 개인정보 수집·이용·전송 — 어떤 정보를 어디에 쓰고 보내나요?

**실제 현장 실증과 결선 시연을 구분합니다.** `talk.silvermedical.kr`은 실제
직원과 어르신의 정보를 사용하는 현장 실증 서비스입니다. 결선 시연 주소인
`chat.silvermedical.kr`에는 실제 기록을 복사하지 않고, 가상의 인물과 상황으로
직접 만든 합성자료를 사용합니다.

| 다루는 정보 | 사용하는 목적 | 저장·처리 위치 |
|---|---|---|
| 직원 이름, 계정, 직종·재직상태, 대화방 참여정보 | 로그인, 업무 소통, 역할별 접근과 퇴사자 차단 | 기관이 관리하는 서버의 데이터베이스 |
| 어르신 식별정보와 직원이 입력한 관찰·건강·상담 등 돌봄 내용 | 보고를 해당 어르신과 연결하고 인수인계·후속 확인·기록 검토에 활용 | 기관 서버의 메시지·업무 데이터베이스 |
| 사진, 음성, 문서와 AI 판독문, 직원 수정문 | 원본 확인, 글자 판독·받아쓰기, 직원 검수 | 기관 서버의 첨부파일 저장소와 데이터베이스 |
| 로그인 세션, 읽음·답글, 수정·승인 등 이용 이력 | 접근 관리, 전달 여부와 변경 과정 확인 | 기관 서버의 데이터베이스·관련 로그 |

연락처·주소 등은 자유롭게 작성하는 대화나 첨부에 포함될 수 있으므로 불필요한
정보를 입력하지 않도록 안내합니다. 기관 운영정책에는 데이터베이스뿐 아니라
로그와 백업에 남는 정보의 범위와 보유·삭제 기준도 포함합니다.

**AI 처리:** 실제 돌봄자료는 기관 내부 AI로 처리하는 것을 원칙으로 합니다.
기존 구현에는 실제자료 표시와 식별정보·민감 문맥을 기준으로 외부 AI 경로를
차단하는 장치가 있습니다. 외부 AI API를 연결하면 선택한 질문이나 자료가
해당 공급자 서버로 전달되므로, 허용 범위는 비민감 질문과 합성자료 또는 사람이
비식별 여부를 확인한 자료로 제한합니다. 자유로운 문장의 모든 개인정보를
자동으로 찾아 제거한다고 보장하지는 않습니다.

9월 13일 격리 후보는 외부 AI 공급자를 비활성화하고 텍스트·이미지·음성을
기관 GPU와 내부 서비스로 처리한 합성 호출을 검증했습니다. Chat과 Talk는
DB·첨부·설정·세션을 분리하지만 같은 GPU·Ollama를 사용하므로 서로의 AI 처리
대기시간에 영향을 줄 수 있습니다. 이 결과가 모든 현장환경의 외부 전송 여부를
증명하지는 않습니다.

**접속·알림:** 공개 접속은 Cloudflare Tunnel을 거칩니다. 알림 기능을 켠
환경에서는 Web Push 또는 Firebase Cloud Messaging이라는 외부 알림 전달
서비스도 사용합니다. 알림에는 돌봄 원문을 넣지 않는 것을 원칙으로 하며,
기기 화면에 표시되는 발신자 정보와 알림 내용도 최소화합니다. 격리 후보는
일반 직원의 음성·영상통화를 시험했지만, 공개 서버 후보의 Web Push는 비활성이며
Firebase 알림 연결도 없습니다. 개발 앱에서 확인한 백그라운드·잠금화면 수신을
공개 앱에 보장하지 않습니다. 통화 연결 시 외부 STUN(기기 연결주소 확인 서비스)을
사용할 수 있으므로, 내부 AI 사용을 모든 데이터의 외부 무전송으로 해석하지 않습니다.

#### 4.5.2 동의·처리근거 — 개인정보 활용의 근거는 무엇인가요?

현장 실증에서 사용하는 직원·어르신 자료에는 기관별 동의·처리 근거와 개인정보
처리방침이 필요합니다. 이번 기술 검수에는 실제 동의서, 대리 동의, 민감정보
처리와 외부 서비스 전달의 적법성 확인이 포함되지 않았습니다. 모든 이용자의
동의나 법적 적합성이 확인됐다고 주장하지 않습니다.

**합성자료와 이름만 가린 실제자료를 구분합니다.** 공개 소스에는 출처를 확인한 합성 시험자료만 포함하며,
재배포 출처를 확인하지 못한 손글씨·음성 원본은 제외합니다. 다만 시연자료가 합성이라고 해도 심사위원의 접속·세션 등
이용정보까지 없어지는 것은 아니므로, 체험 서비스의 접속·세션 정보에도 별도의
수집·보관 기준을 적용합니다.

#### 4.5.3 처리방식·AI 고지 — 이용자에게 어떻게 알리나요?

서비스 화면은 `AI 돌봄 브리핑`처럼 AI가 관여한 기능을 구분하고, 결선 시연에는
합성자료임을 표시합니다. 이 README와 이용자용 가이드도 AI 판독·정리 결과를
원문과 비교한 뒤 사용하도록 설명합니다.

AI 기능의 이름만 표시하는 것으로 안내가 끝나지는 않습니다. 개인정보처리방침과
AI 활용 안내에는 다음 내용을 포함해야 합니다.

- 수집 항목과 이용 목적, 저장 위치, 외부 서비스에 전달하는 정보
- 자료·로그·백업의 보유기간과 삭제 방법, 문의 담당자
- AI가 작성한 초안이라는 표시와 원문 확인·수정 방법
- 외부 AI 기능을 사용할 경우의 전달 대상과 사용 제한

현재 공개 패키지에는 위 내용을 모두 담은 최종 개인정보처리방침과 동의 화면이
포함되어 있지 않습니다.

#### 4.5.4 사람의 확인·수정 — AI가 틀렸을 때 어떻게 고치나요?

직원은 AI가 정리한 결과에서 근거 대화나 원본 첨부로 돌아가 내용을 비교합니다.
사진·문서의 판독문과 음성 받아쓰기에서 틀린 글자·숫자를 고치고, 관련 어르신이
맞는지 확인한 뒤 업무에 활용합니다. 원문이 불분명하거나 결과가 부적절하면
그 내용을 사용하지 않고 담당자에게 확인합니다.

| AI가 돕는 일 | 직원이 확인하고 결정하는 일 |
|---|---|
| 사진·문서를 읽고 음성을 글자로 변환 | 원본과 비교하여 이름·수치·시간 등 잘못 읽은 부분 수정 |
| 관련 어르신과 사건 후보 제시 | 해당 어르신과 실제 상황이 맞는지 확인하고 잘못된 연결 변경 |
| 변화와 이미 한 조치, 남은 확인사항 정리 | 근거 원문과 실제 상태를 확인하고 후속 업무 결정 |
| 업무기록에 활용할 문장 제안 | 필요한 내용만 고쳐 사용하고 최종 기록·승인·서명 책임 |

문서·음성에는 자동 판독문과 직원 확인문을 별도 이력으로 보존하는 구현이
있습니다. 합성시험에서는 미검수 첨부가 있으면 업무 초안 생성과 확정을 서버에서
막고, 다시 읽은 뒤에는 직원의 재확인을 요구했습니다. 기록 후보의 검토·수정·
사용 안 함 제어는 확인했지만, 공식 기록의 최종 확정과 외부 전송은 자동으로
실행하지 않습니다.

#### 4.5.5 AI 피해 방지 — 잘못된 결과의 사용을 어떻게 막나요?

팀은 판독 오류나 잘못된 대상자 연결이 다음 업무에 전달되는 위험을 우선적으로
점검했습니다. 현재 적용한 장치와 남은 확인사항은 다음과 같습니다.

| 우려하는 상황 | 적용한 장치 또는 운영 원칙 | 운영 한계 |
|---|---|---|
| 잘못 읽은 숫자·시간·약 이름을 기록에 사용 | 원본 대조와 직원 수정, 문서·음성 미검수 시 업무 초안·확정 차단 구현 | 실제 사용 전 원본 대조와 재확인이 필요함 |
| AI가 원문에 없는 진단·조치나 완료 사실을 작성 | 입력 근거를 연결하고 결과의 근거번호를 검사하며, 직원이 채택 여부 결정 | 근거 연결만으로 문장 내용의 정확성까지 보장할 수 없어 원문 대조 필요 |
| 다른 어르신의 정보로 잘못된 후속 업무 진행 | 직원이 대상자 연결을 확인·변경하는 검수 절차 | 동명이인·여러 대상자가 함께 등장하는 기록은 사람의 확인이 필요함 |
| AI의 의료·법률 안내를 그대로 따름 | AI는 참고용 초안을 제공하며 실제 투약·처치·평가·서비스 결정은 담당자가 확인 | 최신 지침과 전문가 확인이 필요한 답변의 안내 표시 |
| 다른 직원이나 퇴사자가 자료 열람 | 서버에서 대화방·역할 권한을 검사하고 재직상태·세션을 관리 | 계정·첨부 접근과 퇴사자 차단 상태를 지속적으로 관리해야 함 |
| 시연·GitHub·외부 AI에서 실제자료 노출 | 합성자료 전용 발표환경을 분리하고, 실제 DB·첨부·로그·비밀값을 공개본에서 제외하는 원칙 | 공개 패키지와 Git 이력에 대한 별도 보안검사가 필요함 |

**AI 공급자의 학습 사용 여부:** 검증한 격리 후보는 외부 AI를 사용하지 않습니다.
외부 AI를 연결하는 다른 환경에는 해당 공급자의 데이터 보관·학습 정책과 계정
설정이 적용되므로, 모든 공급자가 입력자료를 학습에 사용하지 않는다고 일괄적으로
보장하지 않습니다. 전송 중 암호화와 공급자의 저장·학습 정책은 서로 다른
보호 항목입니다.

자체 서버 운영은 기관이 자료의 저장 위치와 접근권한을 직접 관리할 수 있다는
장점이 있습니다. 기관은 그 책임에 맞춰 보유·파기기간, 백업 암호화·복원,
로그에 남는 정보를 개인정보 관리 범위에 포함해야 합니다.

모델 변경 직후 질문 시험에서는 응답까지 약 146~207초가 걸렸습니다.
